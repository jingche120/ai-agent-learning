# new-note — 新增／改寫學習筆記

> 使用本 skill 時，先明確告訴使用者：「我用 new-note skill 來寫這篇」。

## 跟 card 的分工（先確認用哪個）

本 skill 產出的是**這個 repo 的長篇筆記**：有操作順序、有編號章節、結尾附檢查清單。如果使用者要的是「把剛才這段對話整理成卡片盒的原子卡、丟進 Heptabase」，那是 [card](../card/SKILL.md)，不要用本 skill。

**判準**：內容的價值來自「順序」→ 用本 skill；價值來自「概念本身、之後可以跟別的概念連起來」→ 用 card。兩者不互斥，同一個主題可以先寫成長文、再另外萃取幾張卡。

## 流程

1. **確認主題與範圍** —— 這篇涵蓋什麼、不涵蓋什麼。範圍不清就先問，不要一邊猜一邊寫。
2. **查證** —— 照 [CLAUDE.md](../../../CLAUDE.md)「寫入前先查證」處理。查證時若發現使用者原本的說法有誤或已過時，**先提出來討論，不要直接改寫**。
3. **照下面的風格骨架產草稿**。

> 提計畫、等使用者同意、草稿確認後才寫檔 —— 這些照 [CLAUDE.md](../../../CLAUDE.md)「操作前先對齊」走，本檔不重複。

## 風格骨架（逐項對照）

- [ ] 以**操作順序**為骨架，用編號章節（`## 0.`、`## 1.` …）從前置確認鋪到收尾
- [ ] 每個步驟後面接一段**為什麼**，說明動機與取捨，不只寫怎麼做
- [ ] 容易混淆的兩個概念一律用**表格並列**，不要寫成散文
- [ ] 用第二人稱「你」，語氣像同事在旁邊講解，不要官方文件腔
- [ ] 概念上容易搞混的地方，開**獨立小節**主動點破（例如「重要：CLAUDE.md 不是『AI 的記憶』」）
- [ ] 程式碼區塊標明語言（`bash`、`json`、`markdown`）
- [ ] 結尾附一份**可直接複製的核取清單**
- [ ] 檔名用**中文**，沿用既有慣例

## 改寫既有筆記時

明確指出你動了哪幾段、為什麼動。

**先 grep 一次再動手**：一個說法在長文裡通常散落多處（設定值、對照表、逐項說明、結尾檢查清單）。只改使用者指到的那一處，整篇會自相矛盾 —— 前面還寫著舊的斷言，讀者翻到哪一段就信哪一段。改動範圍超出使用者原本的要求時，**在計畫階段就講明白會動到幾處**。

## 寫完之後

如果這篇筆記引出了新的專案層級規則（例如確立了某個新的檔案命名慣例），提醒使用者是否要同步更新 [CLAUDE.md](../../../CLAUDE.md)。
