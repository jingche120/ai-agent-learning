# new-note — 新增／改寫學習筆記

> 使用本 skill 時，先明確告訴使用者：「我用 new-note skill 來寫這篇」。

## 跟 card 的分工（先確認用哪個）

本 skill 產出的是**這個 repo 的長篇筆記**，並存入 repository 根目錄的 `new-note/`：有操作順序、有編號章節、結尾附檢查清單。如果使用者要的是「把剛才這段對話整理成卡片盒的原子卡、丟進 Heptabase」，那是 [card](../card/SKILL.md)，不要用本 skill。

**判準**：內容的價值來自「順序」→ 用本 skill；價值來自「概念本身、之後可以跟別的概念連起來」→ 用 card。兩者不互斥，同一個主題可以先寫成長文、再另外萃取幾張卡。

## 存檔位置

- 將完成的長篇筆記存入 repository 根目錄的 `new-note/`。
- 不要把筆記寫進 Skill 目錄 `.agents/skills/new-note/`。
- 檔名使用中文，並沿用 repository 的既有命名方式。
- 如果輸出目錄不存在，請使用者親手建立；只有使用者明確要求代為建立時才建立。
- 如果檔名已存在，先詢問要更新既有筆記還是改用其他檔名，不要直接覆蓋。

## 為什麼需要這個流程

這個 repo 是知識庫，寫錯的成本比寫慢的成本高很多。Claude Code、ChatGPT／Codex 與其他 AI agent 工具都會持續更新，而模型的既有知識可能已經過時——權限模式有幾種、某個快捷鍵是什麼、某個設定欄位叫什麼名字，這些都是**憑記憶回答就可能出錯**的內容。錯誤一旦寫進筆記，之後每次讀都可能被誤導。

所以本 skill 的核心只有一條：**凡是 AI agent 或相關工具的客觀行為，一律查證後才寫；不確定就標出來，不要用流暢的語氣掩蓋不確定性。**

## 流程（必守）

### 1. 先確認主題與範圍

跟使用者確認這篇要涵蓋什麼、不涵蓋什麼。範圍不清就先問，不要一邊猜一邊寫。

### 2. 查證（不准跳過）

把要寫的內容分成兩類：

| 類型 | 例子 | 怎麼處理 |
|---|---|---|
| **客觀行為** | 有哪幾種權限模式、設定檔有哪些欄位、某指令叫什麼、某快捷鍵 | **必須查證**。優先使用目前環境提供的官方文件工具或適用的查證 Skill；若不可用，再查閱該產品的第一方官方文件。不准憑記憶寫 |
| **使用者的經驗與決策** | 「一人開發所以專案規則由自己維護」、「平時直接實作，大改動先規劃」 | 以使用者說的為準，不要用「最佳實務」覆蓋掉 |

查證時如果發現使用者原本的說法有誤或已過時，**先提出來討論，不要直接改寫**。

### 3. 標示不確定的地方

查不到、或查到的資訊互相矛盾時，在草稿裡直接標「（未查證）」或「（版本可能已變動）」交給使用者判斷。**寧可留一個顯眼的問號，也不要寫一句讀起來很肯定的錯話。**

### 4. 照風格骨架產草稿

本 repo 筆記有固定形狀。先讀取目前 agent 適用的專案規則檔（Claude 使用 `CLAUDE.md`，Codex 使用 `AGENTS.md`）；如果對應規則檔尚未建立，仍依下列骨架產生草稿：

- [ ] 以**操作順序**為骨架，用編號章節（`## 0.`、`## 1.` …）從前置確認鋪到收尾
- [ ] 每個步驟後面接一段**為什麼**，說明動機與取捨，不只寫怎麼做
- [ ] 容易混淆的兩個概念一律用**表格並列**，不要寫成散文
- [ ] 用第二人稱「你」，語氣像同事在旁邊講解，不要官方文件腔
- [ ] 概念上容易搞混的地方，開**獨立小節**主動點破（例如「重要：專案規則檔不是『AI 的記憶』」）
- [ ] 程式碼區塊標明語言（`bash`、`json`、`markdown`）
- [ ] 結尾附一份**可直接複製的核取清單**
- [ ] 檔名用**中文**，沿用既有慣例

### 5. 使用者確認才寫檔

草稿先貼在對話裡給使用者看過。**不要直接寫檔**。使用者說 OK 才在 `new-note/` 建立或修改檔案。

改寫既有筆記時，明確指出你動了哪幾段、為什麼動。

## 寫完之後

如果這篇筆記引出了新的專案層級規則（例如確立了某個新的檔案命名慣例），提醒使用者是否要同步更新目前使用的專案規則檔，例如 `CLAUDE.md` 或 `AGENTS.md`；不要未經同意直接修改。
